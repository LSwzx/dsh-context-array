# 这套模型理论上能省多少缓存未命中

用真实的 `usage.jsonl` 算，不靠假设。复现：`node docs/savings-estimate.mjs`。

## 结论（221 个真实请求，2 个会话）

| 指标 | 值 |
|---|---|
| 模型读到的提示词总量 | **81,522,588** token |
| 其中命中缓存 | **81,324,160** token（99.76%） |
| 未命中（按全价计费） | 198,428 token |
| 平均单请求提示词 | 368,880 token |
| 缓存写入 | 0（该路由不上报 cache creation） |

如果**没有缓存**、每个请求都按全价重算，计费输入就是 81.5M token。
实际计费输入 = 未命中 + `r × 命中`（`r` = 缓存命中价 / 未命中价）：

| `r`（命中价/未命中价） | 计费输入等价值 | 相对无缓存节省 |
|---|---|---|
| 0.25 | 20,529,468 | **74.8%** |
| 0.10 | 8,330,844 | **89.8%** |
| 0.05 | 4,264,636 | **94.8%** |
| 0（命中免费，仅作理论上限） | 198,428 | 99.8% |

`r` 取决于你的实际合同价，脚本不假设价格；DeepSeek 官方定价的命中/未命中比大致在
**0.1–0.25** 区间，所以这轮真实数据对应的节省是 **约 75%–90% 的输入侧费用**。

## 为什么节省幅度这么大（而不是"只省 L1–L4 那 18k"）

关键不是 L1–L4 本身有多大，而是**它决定它后面那条链还能不能命中**。

- L1–L4（系统节点 0 + 工具声明）实测约 **17,957 token**，只占平均提示词的 **4.9%**；
- 但请求是"前缀匹配"的：前缀一旦变化，从变化点之后的**整段历史**都变成未命中；
- 平均提示词 368,880 token，而正常一步的未命中只有约 900 token（`uncachedTokens / requests ≈ 898`）；
- 所以**一次前缀破坏 ≈ 400 倍于正常一步的未命中量**。这就是这套架构真正要买的东西：
  不是省 18k，而是防止 369k 整段被打回全价。

按这个模型，如果不做保护、每步都让前缀变化（例如把时间戳塞进系统提示词），
每个请求的计费输入会从 ~900 token 涨到 ~369k token，**单步成本放大约 400 倍**，
整轮会话的输入侧费用就是上面表格中"相对无缓存"的那一列。

## 模型边界（这些都没被这组数字覆盖）

1. **Counterfactual 是"每次请求都冷启动"**。真实世界里更常见的是"偶发一次前缀破坏"：
   那么总损失 = 破坏次数 × 当时的整段提示词。用平均 369k 估算，破坏 10 次 ≈ 3.7M token。
2. **命中并非严格连续前缀匹配**（M1-4 反常现象）。如果 provider 的命中比"最长前导匹配"
   更宽松，那么"破坏前缀"的实际损失会小于上表；反之更贵。受控实验只证明了
   **在该 `in-history` 路由上，提示词变更不会重写系统节点 0**（见 M1-RESULTS），
   但"改工具声明是否必然打穿"仍未被干净地测到。
3. **未计输出 token**：缓存只影响输入侧；输出按输出价另算，与本文无关。
4. **未计时延收益**：命中还能降低首 token 延迟，这里只算 token。
5. 样本来自一个账号、两个会话、DeepSeek `deepseek-flash`；换路由/换价格档要重算。
