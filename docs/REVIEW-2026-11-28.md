## 0. 总体结论

**该 patch 不正确。** 单测与文档主结构大体兑现，但存在：

- 1 个**用户可直接撞上的功能失效**：编辑默认空间的名称/规则对新会话完全不生效（P0-1）。

- 其余为口径与时效性文档问题（P2/P3）。

## 1. P0-0 面板请求 404，四个页签全部不可用（2026-11-28 新增）

**现象**（用户截图，本会话附件）：侧边栏「记忆」面板可以打开，四页签与新手引导正常渲染，但右上角红字「请求失败（404）」，主体一直停在「正在读取空间…」；因为 `overview` 是所有页签的数据源，**空间 / 记忆 / 队列 / 留言箱全部不可用**。

**代码路径**：

- 客户端：[client.js:184](dsh-context-array/client.js#L184) 对非 2xx 响应抛出 `messageOf(payload.error || 'HTTP ' + status)`；响应体不是 JSON 时 `payload = {}`，于是显示「请求失败（404）」。
- 客户端：[client.js:241–252](dsh-context-array/client.js#L241-L252) `refreshOverview()` 失败后 `overview` 保持 `null`；[client.js:370](dsh-context-array/client.js#L370) 在无选中空间时无限显示「正在读取空间…」，**没有错误态、没有重试按钮**。
- 宿主：[index.js:146](dsh-context-array/index.js#L146) 激活时调用 `registerContextArrayApi`；[src/http-api.js:72–74](dsh-context-array/src/http-api.js#L72-L74) 中 `ctx.get('webServer')` 取不到时**静默返回空 disposer**，路由从未注册，且不写任何事件。

**可能原因**（按证据强度排序）：

| # | 假设 | 证据强度 | 说明 |
|---|---|---|---|
| A | 激活时 `webServer` 尚未挂载，注册被静默跳过 | **强** | 这是唯一"无报错、无路由"的路径；重启或新增插件会改变加载顺序。参照 `dsh-client-modules` 用的是 `ctx.inject(['webServer'], …)` 而非 `ctx.get`。 |
| B | 双实例 / 旧客户端 bundle 缓存 | 中 | 页面由另一个进程/旧 bundle 提供，路由注册在别的实例；`curl 127.0.0.1:27303` 与页面同源需确认。 |
| C | 鉴权/网关拦截 | 中 | 未登录 `curl` 得到 401 只能说明网关鉴权存在，**不能**判定路由是否存在；浏览器带 cookie 正常应放行。 |
| D | web-server 前缀匹配或 API 前缀变更 | 弱 | 若命中前缀但分发失败，响应应是 JSON `{error:"UNKNOWN_ROUTE"}`，与截图"非 JSON 404"不符。 |

**定位步骤**（按序执行，先做 1、2 成本最低）：

1. 在页面 DevTools → Network 看 `GET /api/context-array/overview` 的响应体：
   - JSON `{"error":"UNKNOWN_ROUTE"}` → 路由存在、分发不匹配（指向 D）；
   - HTML / 空 / 纯文本 404 → 路由未注册（指向 A/B）。
2. 浏览器地址栏直接打开 `/api/context-array/health`：返回 JSON `ok=true` → 路由在；404/HTML → 不在。
3. 把 `index.js` 的 `ctx.get('webServer')` 改为 `ctx.inject(['webServer'], (webCtx) => …)`（`dsh-client-modules` 同款模式），并补一条 `http-api/registered` 事件；重载后查 `events.jsonl`。
4. 排除双实例：确认 GUI 端口与 `DSH_PROFILE=desktop` 属于同一进程；刷新页面（必要时重启应用）后复测。

**修复候选（本次不实施，供决策）**：

- **必须**：路由注册改为 `ctx.inject(['webServer'], …)`，注册成功/失败各写一条事件（`http-api/registered` / `http-api/unavailable`），不再静默。
- **应当**：面板增加"加载失败 + 重试"状态，`overview` 失败时不能永远停在「正在读取空间…」；四个页签在数据缺失时显示明确错误。
- 可选：把 `/health` 的用途写清（仅诊断，随网关鉴权）。

**验收标准**：重启后打开面板 → `overview` 200 → 四页签有数据；停掉/卸载插件时面板显示错误条与重试，不白屏。

## 3. 问题清单（待修）

### P0-0 面板 API 404，四页签不可用
见第 1 节。修复方向：`ctx.inject(['webServer'], …)` + 注册事件 + 面板错误态与重试。

### P0-1 编辑「默认空间」名称/规则对提示词完全不生效

证据：[index.js:240–242](dsh-context-array/index.js#L240-L242)、[src/db.js:297–312](dsh-context-array/src/db.js#L297-L312)。

未绑定会话的 L4 与 bootstrap 取的是 **config** 的 `spaceName/spaceRules`，而不是 `memory_spaces` 行；`ensureDefaultSpace` 只 `INSERT OR IGNORE`、永不回写；面板「编辑」走 `updateSpace` 只改库。默认空间是唯一空间、绑定表实测 0 行，所以用户改完规则，**任何新会话的 L4 仍是旧文本**——面板提示"仅新会话生效"不成立。

复现：面板改规则 → 开新会话 → 查 `context-array.db` 的 `session_l4_snapshot` 新行，`rules:` 仍旧值。

修复方向：会话装配时优先读 `memory_spaces` 行（config 仅在该 id 不存在时兜底）；`ensureDefaultSpace` 不再作为 L4 真源。
验收：改库/面板改规则后，新会话 L4 与库中 `description` 一致。

### P1-1 留言箱"永久去重"

证据：[src/inbox.js:32–48](dsh-context-array/src/inbox.js#L32-L48)。

去重键只哈希内容、无小时桶；去重查询不看 `status`，同源同目标同内容**永久** `deduped: true`，已读后也发不出去；面板发送时 `sourceSessionId` 恒为 null，"给同一会话发同一句话永远只能成功一次"。实测：首发 `deduped=false` → ack → 再发 `deduped=true`，库中仍 1 行。

修复方向：dedupe key 加 UTC 小时桶（与设计 §3.4 L218 一致），去重范围限定未处理/同小时；面板发送补 `sourceSessionId`（或明确接受匿名）。
验收：同内容一小时内重复发送提示重复；跨小时可再次发送并实际投递。

### P1-2 `inbox_list { status: "all" }` 只返回待读

证据：[src/memory-tools.js:536–542](dsh-context-array/src/memory-tools.js#L536-L542)、[src/inbox.js:51](dsh-context-array/src/inbox.js#L51)。

工具把 `'all'` 转成 `undefined`，而 `listInbox` 解构默认值是 `'pending'`，于是"全部"等于"待读"。实测：1 pending + 1 read，传 `undefined` 只回 1 条。

修复方向：工具层直接把 `'all'` 传给 `listInbox`（或省略该键而不传 `undefined`）。
验收：`inbox_list({status:'all'})` 返回 pending+read。

### P1-3 `deleteSpace` 的默认空间判定写死 `space-default`

证据：[src/spaces.js:62–67](dsh-context-array/src/spaces.js#L62-L67)、[client.js:365](dsh-context-array/client.js#L365)、[client.js:436](dsh-context-array/client.js#L436)。

守卫比较 `DEFAULT_SPACE_ID` 常量，而不是 `config.spaceId`。实测：`resolveConfig({ spaceId:'space-work' })` + `ensureDefaultSpace` → `deleteSpace(db,'space-work')` 返回 `{deleted:true}`，库中空间被清空；此后未绑定会话的隐式默认空间指向不存在的 id，`memory_archive` 持续 `SPACE_NOT_BOUND`，面板显示空空间列表。UI 侧同样写死。

修复方向：`deleteSpace` 增加 `defaultSpaceId` 参数（由 config 传入），UI 以 `/overview` 返回的默认空间 id 或后端标记为准。
验收：自定义 `spaceId` 时默认空间不可删；UI 禁用原因一致。

### P1-4 唤醒限流缺失设计承诺的冷却 / 每源每轮 / 全局上限

证据：[src/inbox.js:135–140](dsh-context-array/src/inbox.js#L135-L140)。

设计 §3.4 L217 明确要求三者，且未标注"保留未实现"；实现只有 `wakeCountLastHour(targetSessionId)`。实测同一分钟内对同一目标连写多条 wake 记录，只有第 11 次才被限流——正是"会话互相唤醒风暴"的入口。

修复方向（择一，写明取舍）：补同 target 冷却（建议 10 分钟）与全局小时上限（`inbox_wake_log` 已够用），每源每轮限制可用事件归因实现或降级为文档未实现项。
验收：冷却期内二次唤醒被降级为排队并记 throttled；全局超限同样降级。
